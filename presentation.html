Sum of Subsets using Backtracking

Design and Analysis of Algorithms
David and Dhurgananth S

The problem

Given n positive numbers and a target M, find every subset whose elements add up to exactly M.

Input: weights w₁ … wₙ and a target M.
Output: all subsets with sum = M.

Why it matters

It is a classic NP-complete decision problem. Brute force checks all 2ⁿ subsets, so we need a way to skip the hopeless ones.

Uses: budget fitting, packing, knapsack-style cryptography, resource allocation.

Where do we see this in real life?

Shopping voucher

A ₹1500 gift voucher must be used exactly. Items cost ₹300, ₹500, ₹600 and ₹700. Which items add up to ₹1500 with nothing wasted?

Cloud server memory

A server has exactly 15 GB free. Jobs need 3, 5, 6 and 7 GB. Which jobs fill the memory with no gap?

Delivery truck

A truck must leave with a 15-tonne load. Parcels weigh 3, 5, 6 and 7 tonnes. Which parcels make a full load?

All three are the same problem: pick items so the total hits one exact number. In this talk we use the numbers 3, 5, 6, 7 and the target 15.

With 4 numbers there are 2⁴ = 16 subsets. Brute force computes all 16 sums and finds one match (yellow). Red sums are already above 15. With 40 numbers there would be over a trillion subsets, which is why we need pruning.

Backtracking approach

At each level we decide about one item: put it in the subset, or leave it out.

Each node of the tree stores a state:

s = sum chosen so far
r = sum of items not yet decided
k = index of the next item
  1. Include item k: go to the left child with s + wₖ.
  2. Exclude item k: go to the right child with s unchanged.
  3. If s = M, record the subset as a solution.
  4. If a branch fails a pruning test, backtrack without exploring it.

  1. Each level of the tree is one number: 3, then 5, then 6, then 7.
  2. A solid line means we include that number.
  3. A dashed line means we leave it out.
  4. A red node is cut off by a pruning rule.
  5. A grey node used all numbers but the sum is not 15.
  6. The yellow node is a solution.

Two pruning rules

Too heavy

s + wₖ > M

Adding the next item overshoots the target. Weights are positive, so no later choice can bring the sum back down. Skip the include branch.

Real life: your basket is already ₹1400 and the next item is ₹700. That makes ₹2100, over the ₹1500 voucher, so you put it back.

Not enough left

s + r < M

Even if every remaining item is taken, the total still falls short of M. Skip the whole subtree.

Real life: you hold ₹300 of items and only ₹700 of items remain. Even buying them all gives ₹1000, never ₹1500, so you stop.

Both tests cost O(1) per node.

Tracing the solution path

  1. Start at the root: s = 0, r = 21.
  2. Include 3: s = 3, r = 18. Bound holds.
  3. Include 5: s = 8, r = 13. Bound holds.
  4. Exclude 6: s = 8, r = 7. Bound holds (8 + 7 = 15).
  5. Include 7: s = 15 = M. Record {3, 5, 7}.
  6. Backtrack and finish the other branches. None reaches 15.

Result

3 + 5 + 7 = 15

The only subset with the required sum. The tree confirms it by exhausting every other branch.

Algorithm

def sum_of_subsets(w, M):
    w.sort(); n = len(w); out = []
 
    def bt(k, s, r, chosen):
        if s == M:                       # solution found
            out.append(chosen[:]); return
        if k == n: return
        if s + w[k] <= M:               # rule 1: not too heavy            chosen.append(w[k])
            bt(k+1, s + w[k], r - w[k], chosen)
            chosen.pop()                  # backtrack
        if s + r - w[k] >= M:           # rule 2: still reachable            bt(k+1, s, r - w[k], chosen)
 
    bt(0, 0, sum(w), [])
    return out
 
print(sum_of_subsets([3, 5, 6, 7], 15))   # [[3, 5, 7]]

Worst case

Still O(2ⁿ). Pruning does not change the bound but cuts the work in practice.

Space

O(n) for the recursion stack and the current subset.

Back to the real-life case

Answer for the voucher

Buy the ₹300, ₹500 and ₹700 items. The total is exactly ₹1500 and the ₹600 item stays on the shelf.

Same answer for the server: run the 3, 5 and 7 GB jobs to fill 15 GB.

What the algorithm saved

It never explored baskets that already went over ₹1500, and it dropped baskets that could not reach ₹1500 even with every remaining item. In our small example that was 10 of 31 tree nodes. In a shop with 40 items the savings are far larger.

Where else: bill splitting, packing a container, filling a time slot with tasks.

Questions you may be asked

Backtracking vs brute force?

Brute force tries everything. Backtracking drops a path as soon as it cannot work.

Is it always faster?

Usually, but the worst case is still O(2ⁿ).

Why sort the numbers?

So the "too heavy" rule is safe: later numbers are never smaller.

Why keep r?

It lets us test "enough left?" in one step without re-adding numbers.

Key takeaways

Model

A binary state-space tree: include or exclude each item.

Prune

Cut a branch when s + wₖ > M or s + r < M.

Result

Same answer as brute force, with fewer nodes explored.
